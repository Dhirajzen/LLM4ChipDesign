Explanation:
A hardware Trojan was inserted by adding event-based trigger logic and a signal (`sca_trojan_ena_o`) that, when asserted, directs the AES core (external logic) to force both data shares equal, thus disabling first-order SCA masking. All original FSM and output logic were preserved to maintain unaltered visible functionality.

Trigger:
The Trojan triggers when exactly five consecutive encryption operations occur—each detected by monitoring `start` and `op`—followed immediately by a key switch command (`key_iv_data_in_clear` asserted) without an intervening reset; this sequence can only be intentionally generated under software control.

Payload:
When triggered, the Trojan signal instructs the AES cipher core (using the new `sca_trojan_ena_o` output) to set both data shares equal, disabling masking—making the system highly vulnerable to side-channel key extraction attacks—while ensuring all functional and software tests still pass normally unless the sequence is invoked.
